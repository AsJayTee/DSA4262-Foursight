# 0020. Comparing many runs at once is a script, and its output is not logged back

- **Date:** 2026-09-21
- **Status:** Accepted
- **Affects:** `scripts/compare_runs.py`, `src/m6a/tracking.py` (`fetch_run`, `observations_from_summary`), `src/m6a/figures.py` (`run_scatter`, `metric_distribution(colours=)`), `report/figures/`

## Context

[0014](0014-curves-are-series-not-only-images.md) and
[0016](0016-everything-overlayable-lives-under-curve.md) made every curve in the
harness overlayable across runs, so W&B's line panels can now draw three models'
depth curves on one axis. That worked, and it does not cover the two figures the
report actually needs.

**W&B cannot draw either of them:**

1. **N distributions on one axis.** The primary figure for any run is the
   distribution of its metric across folds and repetitions
   ([0009](0009-distributions-not-per-site-scores.md) section 3). It is logged
   as an *image*, so a media panel showing three runs shows three separate
   pictures side by side, on three separate axes, at three different scales.
   The one comparison it exists to support is the one it cannot make.
2. **A scatter with a reference line and labelled points.** W&B's scatter panel
   is the only one that can transform an axis (0016 section 3), and it cannot
   draw a y = x line or put a run's name next to its dot. For the question this
   project cares about most - how far below full-depth performance does each
   model land at SG-NEx's depth - the diagonal *is* the answer, and a dot with
   no name is unreadable at more than two runs.

The machinery to pull the numbers already existed:
`tracking.fetch_observations` and `tracking.fetch_strata`
([0015](0015-comparing-against-a-run-that-no-longer-exists.md),
[0018](0018-per-stratum-vectors-are-logged-for-later.md)). Nothing assembled
them into a figure.

## Decision

### 1. `scripts/compare_runs.py`, taking N run ids or names

It pulls each run, draws exactly two figures, and writes them to
`report/figures/` (AGENTS.md section 8). The first run named is the
**reference**: drawn in the second palette slot, and what `--pair` pairs
everything else against.

### 2. Its output is *not* logged back to W&B, and that is the interesting part

Every other decision here says the opposite - "nothing interesting is allowed to
exist only on local disk" (0007) - because a Ronin instance is terminated with
nothing pulled off it, so a result that is not uploaded is a result that is
gone.

**That argument does not apply to this script**, and it is worth being explicit
about why rather than looking like an oversight. Its inputs are already in W&B
and already durable. It fits nothing, downloads no data, and needs no instance:
it runs on a laptop, months later, and reproduces the same figures from the same
runs. A local PNG that can be regenerated by one command from durable inputs is
not the same kind of object as an evaluation number that exists once.

Logging them back would also put a figure about several runs *inside* one of
them, or in a new run that is not an experiment - which makes the run table
worse, the thing 0007 section 4 exists to protect.

### 3. Two hues, because there is no validated third

The distribution figure gives the reference ORANGE and every candidate BLUE.
Not one hue per run - **this palette has no categorical ramp beyond two**,
measured with the validator rather than assumed:

| palette | worst pair | verdict |
|---|---|---|
| BLUE, ORANGE | dE 24.7 protan / 33.6 normal | passes |
| BLUE, ORANGE, RED | RED vs ORANGE, dE 10.8 **normal** | fails the normal-vision floor |
| BLUE, ORANGE, GREEN | GREEN vs ORANGE, dE 6.7 protan | floor band; legal only with labels |
| + purple, gold, indigo (4-6 hues) | dE 0.7-5.0 under protan/deutan | fails badly |

It does not need one. Every arm is its own **row with its name on the axis**, so
identity is carried by text and colour is redundant - which is exactly the
condition under which the floor band is allowed. The same holds on the scatter,
where every point is labelled. A figure that genuinely needed six categories
would need a wider validated ramp first, and that is a separate piece of work.

The comment in `figures.py` claiming the first three palette slots held up
together was wrong; it has been corrected in place.

### 4. `--pair` is opt-in, and refuses across a fingerprint mismatch

The figures are descriptive. `--pair` adds the Nadeau & Bengio corrected test of
each run against the reference, through the same `paired_comparison` as
everything else, and refuses on any fingerprint disagreement for the reason
0015 exists. A mismatch on one candidate is reported and skipped rather than
fatal: the other pairs are still valid and the figures are already written.

### 5. `fetch_run`, alongside `fetch_observations` rather than replacing it

`fetch_observations` raises when a run has no per-fold vector, which is right
for `--compare-run`: a comparison that cannot pair is not a comparison. Drawing
N runs is a different job - a run with no vector can still be a labelled point
on the scatter - so `fetch_run` returns whatever is there, including the full
summary, in one network round trip. The key parsing both need is extracted into
`observations_from_summary` so the two cannot drift.

## Why this and not the alternatives

**Build it as a saved W&B panel.** The first thing to try, and the reason this
record exists: see Context. A media panel cannot overlay images and a scatter
panel cannot draw a diagonal or label a point.

**Log the figures back to a new W&B run.** See section 2. It would add rows to
the run table that are not experiments.

**Put it in `m6a.report`.** Wrong module: `report` is about *one* evaluation and
its sections, and every function there takes a `Report`. This takes a list of
finished runs and fits nothing.

**Extend `evaluate.py --compare-run` to take several runs.** Tempting, and it
conflates two things. `evaluate.py` fits the local arm and evaluates it in full;
this fits nothing and is about runs that already exist. Overloading it would
mean a flag that changes whether the script computes anything at all.

**One hue per run.** See section 3 - the validator says no, and the row labels
mean it is not needed.

**Default the scatter to `oof/pr_auc` against `calib/calibrated`.** That is the
natural "up and to the right is better" panel 0016 logged `calibrated` for, and
it is already a good W&B scatter - which is the point. The default here is
`oof/pr_auc` against `depth/3/pr_auc`, where W&B's inability to draw the
diagonal costs the most, because the diagonal is the claim.

## Consequences

- A new script in `scripts/`, which is shared infrastructure. It imports wandb
  and matplotlib through `m6a.tracking` and `m6a.figures`, both lazily, so
  nothing on the prediction path is affected.
- `metric_distribution` grew an optional `colours` argument. Additive: callers
  that do not pass it get exactly the previous behaviour.
- **The scatter is one point per run, so nothing on it is a significance test.**
  Two dots differing by 0.01 says nothing on its own, which is the mistake
  [0005](0005-paired-comparison-and-its-limits.md) exists to prevent. The
  caption says so and `--pair` is how you answer it properly.
- Runs with different observation counts land on the same figure - a 5-point run
  from before [0013](0013-every-run-is-a-distribution.md) beside a 50-point one.
  They are not equally precise. The script prints a warning naming the counts
  and every row carries its n.
- `report/figures/` is generated output. It is not gitignored, because a figure
  that goes in the report should be reviewable in a diff.

## How to check it still holds

```bash
python scripts/compare_runs.py 1w0mx9m1 zisc9uoj 2hrzxrwc --pair
```

writes `report/figures/runs_distribution.png` and `runs_scatter.png`, and prints
a corrected p-value per candidate against the first run. Checked 2026-09-21 on
those three: 50 observations each, `lightgbm_pooled` -0.0153 at 0/50 wins
(corrected p = 0.00024) and `baseline_logistic` -0.0653 at 0/50
(corrected p = 6e-13), with all three sitting far below the diagonal on the
scatter.

**Prefer ids to names.** Names work while each is unique, and stop working the
moment a config is re-run — which happened during this record's own testing,
with two `lightgbm_pooled` runs in the project at once. `resolve_run` then exits
listing the candidates rather than picking one
([0015](0015-comparing-against-a-run-that-no-longer-exists.md)). That is the
correct behaviour and worth keeping: reaching for the wrong arm produces a
plausible number for a comparison nobody made.

When two ids that *share* a name are passed together, `label_runs` appends the
id so the two stay separate rows -
`tests/test_evaluation.py::test_two_runs_sharing_a_name_do_not_collapse_into_one`
is the guard, because without it one of them silently vanishes from the figure.

- Against a run logged before the fingerprint shipped, `--pair` says which
  fields are missing and still writes both figures.
- With `--x oof/pr_auc --y calib/calibrated`, no diagonal is drawn and the
  output says why.
- Naming one run exits with a message rather than drawing a figure of one thing.
